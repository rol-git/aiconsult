# Архитектура — целевое состояние (общий обзор)

Документ фиксирует, куда движемся от текущего монолита. Детали технологий — позже, здесь только общие контуры.

## Текущее состояние

Монолит Flask + React + Postgres. RAG (LlamaIndex + Chroma) и SocketIO-поддержка живут в одном процессе. LLM — через OpenRouter.

## Куда идём

Разделяем систему на набор контейнеров (docker-compose), чтобы:

- масштабировать горячие части независимо (RAG, WebSocket, STT);
- изолировать тяжёлые модели от API;
- спокойно добавлять новые фичи, не трогая ядро.

## Новые возможности

- **Голосовой ввод** — пользователь диктует, сервис STT превращает в текст, дальше обычный флоу отправки.
- **Геопозиция + карта** — показываем ПВР, очаги, данные с сайта паводок72; координаты пользователя подмешиваются в контекст ответа.
- **Мобильная адаптация (PWA)** — установка на телефон, работа с слабой сетью, офлайн-режим для критичных материалов.
- **Автообновление базы документов** — воркер периодически подтягивает свежие НПА, LLM определяет актуальность и тему, индекс обновляется сам.

## Сервисы (контейнеры)

| Сервис | Роль |
|---|---|
| `gateway` | единая точка входа, TLS, маршрутизация, rate-limit |
| `chat-api` | HTTP API чатов, ask, auth |
| `support-rt` | WebSocket поддержки с операторами |
| `rag-svc` | поиск по документам + вызов LLM |
| `geo-service` | данные карты, интеграция с паводок72 |
| `stt-service` | распознавание речи |
| `docs-ingestor` | фоновая загрузка и классификация документов |
| `client` | React PWA |
| `postgres` | данные + векторы (pgvector) + гео (PostGIS) |
| `redis` | кэш, очереди задач, pub/sub между инстансами WebSocket |

## Хранилища

- **PostgreSQL** — основная база. Вектора через **pgvector**, геоданные через **PostGIS**. Один источник правды вместо отдельной векторной БД.
- **Redis** — кэш ответов, брокер фоновых задач, pub/sub для WebSocket между репликами.

## Брокер сообщений

Отдельный Kafka/RabbitMQ **не нужен**. Redis закрывает все сценарии: очередь задач, pub/sub, кэш, rate-limit. Kafka имеет смысл, только если появится event sourcing/аналитика в реальном времени на нескольких независимых потребителях.

## LLM

Сейчас — OpenRouter. Закладываем возможность переключения на **локальную модель** (отдельный контейнер с OpenAI-совместимым API). `rag-svc` общается с LLM по стандартному интерфейсу, выбор провайдера — конфигом, без переделок кода.

## Пиковая нагрузка

Рассчитываем на массовый трафик в период ЧС. Три слоя защиты:

1. **FAQ-короткое замыкание** — частые вопросы отдаются заготовленными ответами без обращения к LLM.
2. **Семантический кэш** — похожие вопросы получают уже посчитанный ответ.
3. **Очередь с backpressure** — при перегрузке пользователь видит место в очереди вместо ошибки.

Плюс graceful degradation: при недоступности LLM показываем найденные документы «как есть»; при полном отказе — офлайн-страница с телефонами и базовыми инструкциями.

## Офлайн и мобилка

- PWA с service worker: установка на телефон, кэш интерфейса и ключевых материалов.
- Сообщения, отправленные без сети, уходят в очередь и доставляются при восстановлении связи.
- Критичные документы и список ПВР доступны офлайн.

## Наблюдаемость

Базовый набор: структурные логи, метрики (Prometheus + Grafana), трейсы между сервисами. Без этого распределённую систему отлаживать неоправданно больно.

## Что остаётся прежним

- Мультиагентная логика (router + 4 агента) — переезжает в `rag-svc` без изменений.
- Модели БД пользователей, чатов, тикетов — остаются, добавляются новые таблицы (каталог документов, гео-объекты, аудит).
- Интерфейс поддержки с операторами — сохраняется, переключается на Redis-adapter для масштабирования.
